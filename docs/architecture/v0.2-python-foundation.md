## Scope

This note explains the shape of the Python codebase after v0.2 and the reasoning
behind each boundary. It covers no agent behaviour: LangGraph, graph state, and
checkpointing arrive in v0.3, and this release exists so that they arrive onto
something typed and tested.

## Layout

```text
src/enterprise_agents_on_foundry/
    __init__.py          version and a description of the boundaries
    errors.py            EaofError and five subclasses
    config/              settings.py
    infrastructure/      commands.py, environment.py, azd_outputs.py, model_catalog.py
    database/            models.py, validation.py, connection.py, metadata.py
    observability/       timing.py, measurements.py
    cli/                 console.py, verify.py, database_info.py
```

Five boundaries, each named for a responsibility. The top-level `__init__.py`
does not re-export subpackage names, so an import always states which boundary it
crossed.

## Why a `src/` layout

The source directory is not on `sys.path`. The only way to import the package is
to install it, which `uv sync` does in editable mode.

That single property produces the guarantee worth having: what the tests import
is what the wheel contains. Under a flat layout, running anything from the
repository root puts the root on `sys.path`, so imports resolve against source
files whether or not the package was ever installed. A module missing from the
build configuration, a file excluded by the backend, or an uninstalled package
all pass locally and fail the first time the artifact is installed elsewhere.

The cost is that `uv sync` becomes a genuine prerequisite rather than a
convenience. That is an acceptable trade for a failure mode that otherwise
surfaces at the worst possible moment.

## Why uv is retained

uv answers four questions that are frequently conflated.

`pyproject.toml` declares intent: acceptable Python versions, required
dependencies as ranges, optional extras, and build configuration.

`uv.lock` records a resolution: the exact version and hash of every package on
every platform. It is committed, which is what makes two machines and CI install
byte-identical dependencies. The legacy backend carried an unpinned
`requirements.txt`, so no one could state what was actually installed anywhere.

`.venv` is that lockfile materialised on one machine. It is disposable and is not
committed.

`uv run` guarantees a command uses that environment, re-checking the lockfile
first so a stale environment is repaired rather than silently used. Every command
in this repository is written as `uv run ...` for that reason.

Retaining uv was not reconsidered in this release. It was already correct, and
replacing working tooling mid-curriculum teaches nothing.

## Why configuration is centralized

`load_settings()` is the only entry point that reads the environment. Nothing
else in the package or the scripts calls `os.environ`, and a test enforces that
for scripts.

Three properties make the centralisation worth the indirection.

`Settings` is frozen. Configuration that can be mutated after loading can differ
between two points in the same run, and the resulting defect is reported as
intermittent.

The process environment wins over the `.env` file, and reading a `.env` file
never mutates `os.environ`. The legacy backend called `load_dotenv(override=True)`,
which inverts this: a stale file on a developer's disk silently overrode what CI
had deliberately exported.

Validation happens once, at load. Bounds such as the row limit and the query
timeout are declared on the field, so an invalid value is rejected before a
connection is opened rather than discovered against the server. A failure names
the variable and the reason and never echoes the value, because configuration
errors get pasted into issues.

v0.2 moved two further values into `Settings`: `AZURE_MODEL_SKU_NAME` and
`AZURE_MODEL_CAPACITY`. Both were previously read with `os.environ.get` inside
the pre-provision script with inline defaults, so the model shape was declared in
one place and defaulted in another.

## Why scripts are thin adapters

A script parses arguments, calls package functions, prints for a human, and
returns an exit code. It holds no rule.

The reason is reachability. A rule inside a script cannot be imported by the
notebook, cannot be called by a command, and cannot be asserted by a unit test.
It will therefore be reimplemented somewhere else, and the second implementation
is the one that stops matching. v0.1 had already produced three near-identical
subprocess wrappers and one header helper defined twice.

Two tests hold the line: one caps script length, and one asserts that no script
reads an environment variable directly. Both fail loudly rather than eroding.

The three scripts keep their original responsibilities. `preprovision_check.py`
runs the azd pre-provision gate, `bootstrap_database.py` validates the database
and applies the read-only grant, and `write_env_from_azd.py` projects deployment
outputs onto `.env`.

## Why notebooks import package code

A notebook teaches. It narrates a decision and shows a result.

A notebook that defines its own version of a function has created a second
implementation that no test covers, that no command uses, and that drifts the
moment the real one changes. The reader then learns something that is not what
runs.

`notebooks/01_modern_python_foundation.ipynb` therefore imports the package for
every operation it demonstrates, including the CLI commands, which it invokes
through `main()` so that the exit code is visible rather than described.

## Why Azure SQL is isolated behind a database boundary

`database/` is the only part of the package that opens a network connection, and
it is split into four modules by what each one needs.

`models.py` holds types and has no dependencies beyond pydantic. Inputs are
pydantic models, because they cross a boundary and must be validated. Outputs are
dataclasses, because they are constructed internally and validating them again
would only cost time.

`validation.py` is pure. Target resolution and the read-only SQL rules are
functions over strings, which is why every rule about comments, string literals,
stacked statements, and forbidden keywords is unit-tested without a database.

`connection.py` is the only module that touches the network, so everything that
can fail for environmental reasons is confined to one file.

`metadata.py` composes the other three into schema and table discovery, reading
its SQL from `database/queries/*.sql` so that the same statements are reviewed as
SQL, executed by the package, run by the command, and asserted read-only by a
test that walks the directory.

Three independent controls apply to every query, and none depends on a prompt.
The validator rejects anything that is not a single `SELECT` or `WITH`. The row
limit is enforced by fetching one row more than requested, so truncation is
detected and reported rather than hidden. The database principal holds
`db_datareader` with `INSERT`, `UPDATE`, `DELETE`, `ALTER`, and `EXECUTE` denied,
so a destructive statement fails at the server even if the first two controls
were bypassed.

There is no password anywhere in the access model. The Bicep declares no password
parameter, `Settings` has no field that could hold one, and a test asserts that no
field name contains `password`, `secret`, or `key`. The access token is attached
through the ODBC attribute `SQL_COPT_SS_ACCESS_TOKEN`, which keeps it out of the
connection string and therefore out of anything that logs one.

One hole in the boundary is deliberate. `DatabaseClient.raw_connection` exposes
the underlying pyodbc connection for exactly one caller: the administrative grant
in `scripts/bootstrap_database.py`, which must run a statement that is not a
`SELECT`. It is named and documented rather than hidden, so any future use is an
obvious review question.

## Why public SQL access is temporary

The Azure SQL logical server has a public endpoint restricted by firewall rule.
Two rules exist: one for Azure services, and one for a single developer client IP.
Both are conditional on the public endpoint switch, and a test asserts that no
firewall rule can be emitted without it.

This is appropriate for a single-developer teaching environment where the reader
connects from a workstation, and inappropriate for anything else. A public
endpoint with an allowlist is still an endpoint reachable from the internet, and
the allowlist is the only thing between it and the world.

`enablePrivateNetworking` is already parameterised in `infra/main.bicep` and
defaults to `false`. When it is turned on, `platform.bicep` overrides the public
endpoint rather than leaving both paths open. Enabling it requires a virtual
network, a private endpoint, private DNS, and a connectivity story for a
developer workstation that is no longer on the same network as the database.

That is a governance release, not a refactor, and it is scheduled as v0.11 on the
roadmap. Naming it here rather than leaving it implicit is the point: a temporary
property that nobody wrote down becomes a permanent one.

## Errors and exit codes

Every error the project raises inherits from `EaofError`.

| Error                       | Situation                                     |
|-----------------------------|-----------------------------------------------|
| `ConfigurationError`        | A setting is missing or invalid                |
| `AzureEnvironmentError`     | A tool, sign-in, or Azure query is unavailable |
| `UnsafeDatabaseTargetError` | The target or the operation was refused        |
| `DatabaseConnectionError`   | The database could not be reached              |
| `QueryValidationError`      | The SQL is not a single read-only statement    |

The commands map these onto three exit codes: `0` passed, `1` ran and failed, `2`
could not run. The distinction between `1` and `2` is the one that matters
operationally. A missing ODBC driver and a broken database are different
problems, and a tool that reports both as `1` sends people to debug the wrong
system.

## Testing

| Suite                | Command                        | Needs        |
|----------------------|--------------------------------|--------------|
| Unit                 | `uv run pytest -m "not azure"` | Python only  |
| Azure integration    | `uv run pytest -m azure`       | A subscription and the ODBC driver |

The split is by requirement, not by coverage. A suite that needs a subscription
to be meaningful is a suite that gets skipped, so anything decidable without
Azure is decided in the unit suite: parsing, validation, comparison, row limits,
and exit codes are pure functions specifically so they can be.

The Azure suite asserts what only a live database can. It skips with a stated
reason rather than failing when the environment is absent, so a fresh clone can
still run the whole command.
