## What v0.3 left unfinished

v0.3 fixed the control flow. The graph became explicit, the model lost its
tools, and every statement passed a validator before execution. That release
solved who decides what.

It did not solve how the graph learns what happened. Two boundaries were still
untyped, and both leaked their most interesting outcomes.

The query boundary was a bare `Callable[[QueryRequest], QueryResult]`. A refusal
and an outage both arrived as exceptions, so the two outcomes a reader most
wants to distinguish were invisible in the signature. Worse, a query that ran
and matched nothing was indistinguishable from a query that ran and matched
something, because both returned a `QueryResult`.

The model boundary had the same shape of problem. A model that answered
unusably raised, which forced the graph to express routing as exception
handling. Nothing recorded what a call cost, so no measurement of model
behaviour was possible without instrumenting each call site.

## What v0.4 changes

Expected outcomes become values. Only a programming error still raises.

```text
Question
  -> draft_sql()      -> ModelInvocation[SqlGenerationResult]
  -> assert_read_only_sql()
  -> QueryTool.execute() -> QueryToolResult
  -> write_answer()   -> ModelInvocation[str]
  -> AgentOutput
```

Both boundaries now answer three questions in their return type: what happened,
what came back, and what it cost.

## The query tool contract

`database/tool.py` declares one operation, `execute`, and one result type. The
status enumeration carries four cases, and the split between the first two is
the point of the release.

| Status | Meaning | Carries |
| --- | --- | --- |
| `success` | The statement ran and matched rows | A result |
| `empty` | The statement ran and matched nothing | A result with zero rows |
| `rejected` | The boundary refused to run it | A reason |
| `failed` | Execution was attempted and did not complete | A reason |

`QueryToolResult.__post_init__` refuses a value that contradicts its own status,
so a caller cannot read rows from a refusal or a reason from a success. That
invariant is enforced in the dataclass rather than trusted at each construction
site, because fakes implement this contract too, and a fake that drifts from the
real boundary is a test that proves nothing.

This is a boundary rather than a general-purpose tool. The model cannot call it,
cannot choose it, and cannot supply anything to it that has not already passed
`assert_read_only_sql`.

## The model contract

`agents/model.py` remains the only module that builds a chat client or turns a
response into a typed value. v0.4 adds three things to it.

`ModelConfiguration` resolves the deployment once and is then passed explicitly.
Two of its properties are defaulted from module constants rather than from
settings, because they are facts about a model version that should change with a
reviewed diff instead of being tuned per environment.

`ModelInvocation` wraps every call, pairing the value with `ModelCallMetadata`.
Latency and purpose are recorded at the boundary, so cost measurement needs no
instrumentation at the call sites.

Structured output moves from request to guarantee. `STRUCTURED_OUTPUT_METHOD` is
`json_schema`, which is constrained decoding against the schema. The legacy
agent asked for JSON in the prompt and parsed whatever came back.

Two constants encode hard-won facts about deployments. `SUPPORTS_TEMPERATURE`
is `False` because recent reasoning-oriented deployments reject any explicit
sampling temperature and fail the whole request rather than ignoring the
parameter. `MAX_MODEL_RETRIES` is `2` and covers transport only: a rejected or
malformed answer is never retried here, because that is the graph's single
repair attempt, and it must stay visible in state.

## The model is allowed to decline

The most consequential addition is `GenerationDisposition`. Before v0.4 the
model was asked for SQL and had no way to say that SQL was the wrong answer.

| Disposition | The model is saying |
| --- | --- |
| `ready` | Here is a statement |
| `clarification_required` | The question is ambiguous |
| `unsupported` | This database cannot answer it |

A model with no way to decline invents. Giving it two structured ways to refuse
removes the pressure to guess a table that does not exist, and both refusals are
routed by the graph rather than parsed out of prose.

`AgentOutcome` grew to match, so the outcome a caller receives now distinguishes
six terminal states rather than a success and a failure.

| Outcome | Reached when |
| --- | --- |
| `succeeded` | Rows were returned and described |
| `empty` | The query ran and matched nothing |
| `clarification_required` | The model asked for a better question |
| `unsupported` | The question cannot be answered from this schema |
| `rejected` | A statement failed the read-only boundary |
| `failed` | The repair budget was spent |

`empty` deserves its own outcome because "no customers match" is a correct
answer, not a failure, and a caller that cannot tell the two apart will report
an outage every time a filter is narrow.

## Topology after the change

The graph still has seven nodes. Two things moved.

The terminal node is now `finalize` rather than `fail`, because a run that ends
without rows is not necessarily a failure. One node builds `AgentOutput` for
every non-success outcome, so the shape a caller receives does not depend on
which branch produced it.

Routing functions went from three to four. The additional one routes on the
generation disposition, which did not exist before.

## Alternatives that were rejected

Returning `None` for refusal. It collapses four statuses into two and forces the
caller to reconstruct the reason from context that is no longer available.

Raising a typed exception per outcome. This keeps the information but puts
routing logic in exception handlers, where it is invisible to a reader following
the graph and awkward to exercise in a test.

Retrying a malformed model answer inside the model boundary. It would hide an
attempt that the repair budget is supposed to bound, and the count in state
would no longer describe what actually happened.

Making the model choose between deployments. One deployment, no fallback list,
and no routing policy. Model selection is a later concern, and implementing it
here would have meant designing a policy with no evidence to justify it.

## What this release does not address

The agent still runs in whatever process starts it, authenticated as whoever
started it. Nothing here packages it, gives it an identity, or exposes it over a
protocol. That is v0.5.
