## What changes, and what does not

v0.4 finished the agent core. Everything it did ran inside a Python process that
someone started by hand, held a database connection that someone had already
authenticated, and answered a caller sitting in the same process.

v0.5 changes only where that core runs. The graph is untouched. What is new is a
protocol adapter, a container, and an identity of its own.

That last item is the whole release. Moving from "runs as the developer" to
"runs as itself" is where a hosted agent actually breaks, and most of this
document is about identity for that reason.

## The protocol boundary

The host requires a graph whose state carries a `messages` list. The production
graph has no such field, and reshaping it to fit would have coupled the core to
one protocol.

The dependency arrow points one way instead. `hosting/` imports `agents/`, and
nothing in `agents/` imports `hosting/`. A core coupled to Responses would need
changing again for the next protocol, and every test of the core would need a
protocol fixture.

`hosting/responses.py` performs exactly two mappings.

Inbound, `extract_user_text` takes the latest human message and nothing else.
The host sends prior history followed by the current turn. Non-text content,
such as an image part, and a blank message both return `None` rather than being
coerced into a question.

Outbound, `render_output` maps each terminal `AgentOutcome` onto one
caller-facing sentence. Distinct outcomes stay distinct, but refusals and
failures render to fixed text, so an internal reason, a driver error, a token, or
a connection string cannot cross this boundary.

`build_adapter_graph` wraps the production graph in a one-node `MessagesState`
graph, which is the shape `ResponsesHostServer` requires. `hosting/app.py` adds
only wiring: real settings, a real database client, a real model, and a port.

## The container boundary

The image reproduces the layout the code expects, because
`config.settings.repository_root` resolves paths relative to the source tree.
The package stays under `/app/src` and `database/queries` is copied beside it.

Three decisions in the Dockerfile matter more than their size suggests.

`pyodbc` needs ODBC Driver 18, a system package rather than a wheel. That single
`apt-get` layer dominates the 645 MB image.

The image runs as an unprivileged user, `appuser`, uid 10001.

Dependency resolution is locked with `uv sync --frozen`, so the image cannot
silently drift from `uv.lock`.

BuildKit cache mounts are deliberately absent. ACR Tasks builds this image with
the classic builder, which does not support `RUN --mount`, and `remoteBuild` in
`azure.yaml` sends only the small source context to ACR rather than pushing 645 MB
from a workstation.

## Three identities, one of which runs

This is the section that explains most first-deployment failures.

Locally, `DefaultAzureCredential` resolves to the developer. That account is the
Entra administrator on the SQL server and already holds roles on the Foundry
account, so everything works and the agent's own permissions are never
exercised.

In Foundry, the same `DefaultAzureCredential` resolves to the agent instance
identity, a distinct service principal named after the account, project, and
agent. It begins with no roles and no database user.

| Identity | Principal | Run-time role | Survives redeploy |
| --- | --- | --- | --- |
| Caller | The developer or calling application | Authorized to invoke the agent | Not applicable |
| Agent instance | `<account>-<project>-<agent>-AgentIdentity` | Authenticates to the model and the database | Yes |
| Agent blueprint | `<account>-<project>-<agent>-<guid>-AgentIdentityBlueprint` | None required | No |
| User-assigned | `id-eaof-dev` from `identity.bicep` | None at run time | Yes |

The fourth row is the trap. `rbac.bicep` grants roles to the user-assigned
managed identity, and the hosted agent does not run as it. Granting that
identity more permission has no effect on the running agent.

The instance identity name carries no version suffix, so it is stable across
deploys. Only the blueprint identity is per version.

## Model access without a key

The Foundry account is provisioned with `disableLocalAuth: true`. There is no
API key to fall back on and none to leak, so `agents/model.py` builds a bearer
token provider over `DefaultAzureCredential` for the Cognitive Services scope.

That decision is why the agent identity needs an explicit role. Inference on a
keyless account requires `Cognitive Services OpenAI User` on the Foundry
account. Until it is granted, the model call raises, the adapter renders
`FAILED_MESSAGE`, and the caller sees a generic error with no indication that
the cause was authorization.

## Read-only database access

The agent identity authenticates to Azure SQL with an Entra token, so it needs a
contained database user created with `CREATE USER ... FROM EXTERNAL PROVIDER`.
No login and no password exist anywhere in this path.

It receives `db_datareader` and an explicit `DENY` on every write verb. That is
the durable control. The validator in `database/validation.py` is defence in
depth, and the database permission is what holds if the validator ever has a
bug.

Reachability is worth separating from authentication. The `AllowAllWindowsAzureIps`
firewall rule already admits Azure-hosted callers, so no firewall change was
needed. A blocked network appears as a timeout. A missing database user appears
as `Login failed for user '<token-identified principal>'`.

## Deployment and versioning

`azd deploy` builds the image in ACR, publishes it, creates an agent version,
and polls until that version reports `active`. Versions are immutable and
monotonic.

Two provisioning changes were required. `AZURE_AI_PROJECT_ID`, the ARM resource
id of the Foundry project, becomes a Bicep output because azd resolves the
hosted agent target from it. `ENABLE_CONTAINER_REGISTRY` moves from `false` to
`true`, because a hosted agent must publish its image somewhere.

## Defence in depth for writes

Three independent layers refuse a write, and each holds if the others fail.

| Layer | Control | Fails to |
| --- | --- | --- |
| Intent | The model classifies the request as unsupported | Draft any SQL |
| Validation | `assert_read_only_sql` rejects the statement | Reach the driver |
| Permission | `db_datareader` and explicit `DENY` | Execute at the database |

Every refusal reaches the caller as fixed text. A caller who learns why a
statement was refused learns about the validator, and the next attempt is better
informed.

## Alternatives that were rejected

Reshaping the graph to carry `messages`. It would couple the core to one
protocol and force a protocol fixture into every core test.

Returning the exception text to the caller. It converts the failure surface into
a description of internal structure and risks leaking a driver message or a
connection string.

Granting the user-assigned managed identity more permission. It is the intuitive
fix and it does nothing, because that identity is not the one running.

Enabling local authentication on the Foundry account. A key would remove the
identity work entirely, at the cost of a credential to store, rotate, and leak.

## Known weakness in this design

Rendering every exception to one sentence protects the caller and cost real
diagnostic time during this release: an authorization failure was
indistinguishable from any other error, and the cause was found only by calling
the endpoint directly. Logging the exception type server-side, without the
message, would preserve the boundary and restore diagnosability.
