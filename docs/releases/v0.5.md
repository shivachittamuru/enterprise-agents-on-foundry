## Scope

This release changes where the agent runs, not what it does. The graph is
untouched.

What is new is a Responses protocol adapter, a container image, and a run-time
identity: the agent now runs as a Microsoft Foundry Hosted Agent and
authenticates to the model and to Azure SQL as itself rather than as the
developer.

No streaming, no conversation memory, no evaluation harness, and no scale
evidence. Checkpointing remains deferred to v0.8.

## What shipped

A seventh boundary, `hosting/`, with two modules.

| Module | Responsibility |
| --- | --- |
| `responses.py` | Inbound text extraction, outbound outcome rendering, and the adapter graph |
| `app.py` | Production wiring and the host entry point |

The dependency arrow points one way. `hosting/` imports `agents/`, and nothing
in `agents/` imports `hosting/`, so the core stays usable without a protocol
fixture.

`Dockerfile` builds a 645 MB image that reproduces the repository layout the
code expects, installs ODBC Driver 18, resolves dependencies from `uv.lock` with
`--frozen`, and runs as an unprivileged user.

`azure.yaml` declares the agent, its protocol, its container resources, and the
environment variables Foundry injects. It contains no secrets, because every
credential in this release is an Entra token acquired at run time.
`remoteBuild: true` builds the image inside ACR, so only the small source
context crosses the network.

Two infrastructure changes were required. `AZURE_AI_PROJECT_ID` becomes a Bicep
output, because azd resolves the hosted agent target from it and fails the
publish step without it. `ENABLE_CONTAINER_REGISTRY` moves from `false` to
`true`.

`rbac.bicep` gained an `AcrPull` assignment for the Foundry project identity,
which is the principal that pulls the image. The user-assigned managed identity
it already granted is not that principal.

## Verification

```console
uv run pytest -m "not azure"
uv run pytest -m azure
azd deploy text-to-sql-agent
azd ai agent show text-to-sql-agent
```

The deployed endpoint answers over the Responses protocol. Reads return correct
results, and write requests are refused before any SQL is drafted.

Use a direct HTTPS call rather than `azd ai agent invoke` when verifying output.
During this release, `azd ai agent invoke` returned an empty `output` array for
responses that the same endpoint, session, and conversation returned correctly
over HTTPS.

## Identity, and why most failures happened here

Locally, `DefaultAzureCredential` resolves to the developer, who is already the
SQL Entra administrator and already holds Foundry roles. In Foundry it resolves
to the agent instance identity, which begins with no roles and no database user.

Three grants were required, and none of them is the identity that `rbac.bicep`
had been granting.

| Grant | Scope | Symptom when missing |
| --- | --- | --- |
| Contained user with `db_datareader` | AdventureWorksLT | The container exits at startup and the session never becomes ready |
| `Cognitive Services OpenAI User` | Foundry account | Every question returns a generic error |
| `Monitoring Metrics Publisher` | Application Insights | Telemetry export fails repeatedly, answers unaffected |

The database user is created with `CREATE USER ... FROM EXTERNAL PROVIDER` and
receives an explicit `DENY` on every write verb. No login and no password exists
anywhere in this path.

Role assignment propagation is not immediate. During this release an identical
call failed and then succeeded minutes later with no other change.

## Limitations

The identity grants are not reproducible. The agent instance identity does not
exist until the first deploy, so its three grants cannot live in the
provisioning templates and were applied by hand. A fresh `azd up` in a new
environment reproduces all three failures. A post-deploy hook is the fix, and it
is not implemented.

No streaming. The agent answers one turn at a time and returns the whole answer
at once, so a long query looks like a pause.

No conversation memory. The session and conversation identifiers are carried by
the protocol, but each question is answered independently.

One replica, no scale evidence. The container is provisioned with 0.5 vCPU and
1 GiB, and nothing here measures concurrency or cold start.

Latency is not attributed. The end-to-end number mixes two model calls, one
query, and session start-up, and this release does not separate them.

Failures are opaque by design, and that cut both ways. Rendering every exception
to one sentence protects the caller, and during this release it also masked an
authorization failure as a generic error. Logging the exception type
server-side, without the message, would keep the boundary and restore
diagnosability.
