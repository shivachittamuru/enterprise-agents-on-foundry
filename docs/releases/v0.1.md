## Scope

This release establishes the baseline. It analyses the brownfield LangGraph
backend, bootstraps a modern Python repository, and provisions the Azure
foundation that later releases build on.

No agent is built. No LangGraph code is migrated. The Text-to-SQL problem stays
simple throughout the curriculum, because the subject is the platform and the
architecture around the agent.

## What shipped

Analysis of the brownfield backend is recorded in four documents under
[../current-state](../current-state/backend-inventory.md), each claim citing a
path under `../langgraph-agents-on-azure/backend`.

Four architecture decision records cover the new repository, the Azure SQL
dataset choice, the azd and Bicep lifecycle, and the model selection deviation.

The repository baseline is Python 3.12 with uv, a committed lockfile, four
runtime dependencies, an optional `database` extra, and configured ruff, mypy,
and pytest.

Five setup modules under `src/enterprise_agents_on_foundry/setup/` provide typed
configuration, read-only SQL validation and database-target resolution,
prerequisite checks, Azure context checks, model catalog checks, and measurement
capture.

> [!NOTE]
> v0.2 split that single `setup` package into five named boundaries. The
> reasoning is in [ADR 005](../adr/005-use-src-layout-and-thin-adapters.md).

Nine Bicep files under `infra/` provision the foundation, driven by `azure.yaml`
with pre-provision and post-provision hooks.

A planned evaluation dataset of 20 cases is defined in
[../../evals/datasets/legacy-baseline.jsonl](../../evals/datasets/legacy-baseline.jsonl),
covering expected behaviour and metadata only.

The bootstrap notebook
[00_brownfield_baseline_and_azure_bootstrap.ipynb](../../notebooks/00_brownfield_baseline_and_azure_bootstrap.ipynb)
walks through the whole release, importing the helper modules rather than
duplicating them.

## Before and after

| Dimension | Before | After |
| --- | --- | --- |
| Python setup | Manual Conda environment | Python 3.12 with uv and a committed lockfile |
| Dependencies | 31 exact pins, no lockfile, no groups, one undeclared import | Ranges plus `uv.lock`, dev group, optional native extra |
| Runtime packages | 31 | 4 |
| Repository structure | Flat backend folder mixing agents, API, notebooks, evaluations, and binaries | Separated source, infrastructure, database, docs, notebooks, evals, scripts, tests |
| Data source | 892 KB SQLite file committed twice and baked into the image | Azure SQL serverless with AdventureWorksLT populated by the platform |
| Committed database binaries | 5 files, roughly 5 MB, including real conversation state | None, enforced by `.gitignore` and a test |
| SQL safety | Prompt text asking the model to avoid DML | Read-only principal plus a deterministic single-statement validator |
| Authentication | API keys and passwords in environment variables | Microsoft Entra only, with local auth disabled at the resource |
| Infrastructure | Manual Docker, ACR, Web App, and AKS steps | Subscription-scoped modular Bicep under the azd lifecycle |
| AI platform | Classic Azure AI Foundry assumptions | Foundry account with project management and a child project |
| Monitoring | Configured against a mismatched variable name, silently inactive | Workspace-based Application Insights provisioned as infrastructure |
| Path resolution | Relative to the working directory | Anchored on the package location |
| Configuration | Environment read once at class definition, `None` in `str` fields | Validated, frozen settings with process environment taking precedence |
| Automated tests | None | Configuration, SQL safety, structure, and infrastructure contracts |
| Static analysis | None | ruff lint and format, mypy strict |
| Teardown | Manual portal steps | `azd down --purge` |

## Measurement definitions

Measurements are captured by
[measurements.py](../../src/enterprise_agents_on_foundry/observability/measurements.py)
and written as JSON so later releases can compare against this baseline.

Setup measurements record the number of manual steps a developer performs before
and after, and the number of automated validation steps that replace them. The
legacy path required installing Conda, creating an environment, activating it,
installing from `requirements.txt`, copying `.env.example`, obtaining an Azure
OpenAI key, populating the key, and locating the SQLite file. The current path is
`uv sync`, `azd auth login`, `azd provision`, and `uv run python
scripts/bootstrap_database.py`.

Provisioning measurements record the wall-clock duration of `azd provision` and
the resulting resource inventory.

Database measurements record the schema count, the table count, the total
approximate row count, the connection probe latency, and the latency of the
representative join and aggregate query in
[03_smoke_product_categories.sql](../../database/queries/03_smoke_product_categories.sql).
The row counts come from partition metadata rather than `COUNT(*)`, which keeps
the query cheap on a serverless database.

Model measurements record smoke-test latency once a model deployment exists.

Repository measurements record the runtime dependency count, the committed
binary size, and the test count.

Capture them with:

```console
uv run --extra database python scripts/bootstrap_database.py --measurements-out artifacts/v0.1-measurements.json
```

`artifacts/` is excluded from version control, so a measurement run never
produces a commit.

## Verification

Six commands constitute the quality gate for this release.

```console
uv sync
uv run pytest
uv run ruff check .
uv run ruff format --check .
uv run mypy src scripts
az bicep build --file infra/main.bicep
```

All six pass with no errors and no warnings.

## Known deviations

The work order specified `gpt-5.1-mini`. That model is published in neither the
regional catalog nor the quota list for `westus3`. The evidence and the chosen
substitute are recorded in
[../adr/004-model-deployment-selection.md](../adr/004-model-deployment-selection.md),
which is flagged for owner review. No fallback logic exists in the codebase, so a
configured model that cannot be deployed stops provisioning with an explicit
message rather than being replaced.

## Deferred to later releases

Durable conversation checkpointing, application instrumentation, the replacement
service layer with its CORS and error-handling constraints, and the single
LangGraph agent implementation are all deferred. The reasons are recorded per
risk in
[../current-state/modernization-risks.md](../current-state/modernization-risks.md).
