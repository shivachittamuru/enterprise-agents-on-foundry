## Scope

This release makes the Python codebase ready for an agent. It replaces the single
`setup` package with five boundaries named for responsibility, introduces a typed
error hierarchy, adds two command line entry points, and splits the tests into a
fast offline suite and an Azure suite.

No agent is migrated. LangGraph, graph state, and checkpointing are v0.3. The
order is deliberate: migrating an agent onto an untyped, untested foundation
produces a migration nobody can verify.

No Azure resources changed. Every optional capability flag introduced in v0.1 is
still `false`.

## What shipped

The package now has five boundaries under `src/enterprise_agents_on_foundry/`:
`config`, `infrastructure`, `database`, `observability`, and `cli`, plus
`errors.py` at the root. The top-level `__init__.py` does not re-export
subpackage names, so an import always states which boundary it crossed.

`errors.py` defines `EaofError` and five subclasses that name five distinct
situations, replacing a mixture of custom types, bare `ValueError`, and
`PermissionError`. The choice of subclass determines the exit code a command
returns.

`config/settings.py` gained `AZURE_MODEL_SKU_NAME` and `AZURE_MODEL_CAPACITY`,
the last two values that were being read with `os.environ.get` inside a script.
`load_settings` now raises `ConfigurationError` with a message that names the
variable and the reason without echoing the value.

`infrastructure/commands.py` replaces three near-identical subprocess wrappers
with one that never raises, so a report can be assembled from partial results
rather than aborting at the first missing tool.

`infrastructure/azd_outputs.py` separates parsing from invocation, so every rule
about malformed payloads, blank values, and non-object JSON is unit-tested
without azd installed.

`database/` splits into `models.py`, `validation.py`, `connection.py`, and
`metadata.py`, so that only one module opens a network connection and the rest
can be tested as pure functions.

Two console scripts are declared in `[project.scripts]`:

```text
uv run eaof-verify     # is this workstation and Azure environment ready
uv run eaof-db-info    # what is in the database, read-only
```

The three scripts under `scripts/` are now adapters. Two tests enforce that: one
caps script length, and one asserts that no script reads an environment variable
directly.

The test suite is split into `tests/unit/` and `tests/integration/`. The Azure
suite is marked `azure` and skips with a stated reason when the environment is
absent.

The notebook
[01_modern_python_foundation.ipynb](../../notebooks/01_modern_python_foundation.ipynb)
covers the twelve topics of this release and imports the production package for
every operation it demonstrates, including the CLI commands, which it invokes
through `main()` so the exit code is visible rather than described.

## Before and after

| Measure                          | v0.1 | v0.2 | Note                                          |
|----------------------------------|------|------|-----------------------------------------------|
| Direct environment reads         | 4    | 0    | All four were in `preprovision_check.py`       |
| Duplicate helper implementations | 6    | 0    | One header helper, three wrappers, two constants |
| Package CLI commands             | 0    | 2    | `eaof-verify`, `eaof-db-info`                  |
| Package boundaries               | 1    | 5    | `setup` replaced by named responsibilities     |
| Tests                            | 123  | 196  | 186 unit, 10 Azure integration                 |
| Ruff findings                    | 0    | 0    | Held at zero across the refactor               |
| Mypy findings (strict)           | 0    | 0    | Held at zero across the refactor               |

Two of these need comment.

Each of the four direct environment reads carried its own inline default, so the
model SKU was declared in `Settings` and defaulted in a script. A change to one
did not reach the other.

None of the six duplicate implementations were wrong. They were the second copy,
which is the one that stops matching the first.

## Measurement definitions

Measurements are captured by
[measurements.py](../../src/enterprise_agents_on_foundry/observability/measurements.py)
and written to
[v0.2-measurements.json](v0.2-measurements.json) by the release notebook.

`Measurement` gained a `baseline` field in this release, so a before and after
claim carries the number it was derived from rather than referring to it.

Direct environment reads counts occurrences of `os.environ` and `os.getenv`
across the package and the scripts. A test asserts this stays at zero for
scripts.

Duplicate helper implementations counts functions with the same responsibility
defined more than once: `_print_header` in two scripts, three subprocess wrappers
in `prereqs.py`, `azure_env.py`, and `model_catalog.py`, and the model name and
version fallback constants repeated between the notebook and the script.

Test durations are wall-clock for `uv run pytest` including process startup, not
the pytest-reported figure, because process startup is part of what a developer
waits for.

## Verification

Every command below passed on the authoring machine.

```text
uv sync
uv run ruff check .
uv run ruff format --check .
uv run mypy src scripts
uv run pytest -m "not azure"
uv run eaof-verify
```

`uv run pytest -m azure` and `uv run eaof-db-info` require the ODBC driver.

## Known limitation

`ODBC Driver 18 for SQL Server` was not installed on the authoring machine, so
nine of the ten Azure integration tests skipped with a stated reason and
`eaof-db-info` returned exit code `2`. Both behaved as designed, and the
skip and the exit code are themselves the evidence that the unavailable path is
distinguished from the failing path.

Install it with `winget install --id Microsoft.msodbcsql18` on Windows, then open
a new terminal so the driver registration is picked up, and re-run:

```text
uv run pytest -m azure
uv run eaof-db-info
```

The database latency measurements in `v0.2-measurements.json` are therefore
absent rather than zero. A later release will record them.

## Not in this release

No LangGraph, agent, graph state, or checkpointing. No FastAPI, hosted agents,
Foundry IQ, long-term memory, MCP, Teams distribution, or external hosting. No
new Azure resources and no change to the AdventureWorksLT dataset.

The Azure SQL server still has a public endpoint restricted by firewall rule.
That is appropriate for a single-developer teaching environment and nothing else.
Private networking is parameterised and defaults to `false`; enabling it is
scheduled as a governance release. The reasoning is in
[v0.2 Python Foundation](../architecture/v0.2-python-foundation.md).
